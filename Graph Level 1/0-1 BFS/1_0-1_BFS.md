# 0–1 BFS: Shortest Paths with Edge Weights 0 and 1

Ordinary BFS finds shortest paths when every edge has the same unit cost. Its queue processes vertices in increasing order of their distance from the source, measured in **number of edges**.

What changes if some edges cost 0 and others cost 1?

We must minimize the **sum of edge weights**, not the number of edges. A path with more edges can still be cheaper. **0–1 BFS** maintains the required processing order using a deque: zero-cost moves go to the front, and one-cost moves go to the back.

## 1. Problem Statement

Given a graph in which every edge has weight either **0 or 1**, find the minimum total cost from a source vertex `s` to every vertex.

- A path's cost is the sum of the weights of its edges.
- The source has distance 0: staying at the source uses no edges.
- An unreachable vertex has no finite distance; the implementation prints `-1` for it.

The algorithm works for both directed and undirected graphs. The illustration and complete program below use an **undirected** graph.

For example, from vertex 1 to vertex 6:

```text
1 -> 2 -> 4 -> 5 -> 6
Cost = 0 + 1 + 0 + 0 = 1
```

This path uses four edges, but its total cost is only 1.

## 2. Why an Ordinary BFS Queue Is Not Enough

With unit-weight edges, a move from distance `d` always leads to a candidate distance of `d + 1`. A FIFO queue naturally finishes the current distance layer before the next one.

With weights 0 and 1, a move can instead lead to:

| Edge weight | Candidate distance from a vertex at distance `d` | Where to insert an improved candidate |
| --- | --- | --- |
| 0 | `d` | Front of the deque |
| 1 | `d + 1` | Back of the deque |

A zero-weight edge does not increase the cost, so its destination should be considered before candidates waiting at the next cost level.

The weights belong to **edges**, not vertices. The front is not a collection of “weight-0 vertices,” nor does being at the back mean a vertex's total distance is 1. What matters is the candidate's **total distance from the source**.

## 3. Relaxation: Update Only When the Distance Improves

Initially:

```text
dis[s] = 0
dis[every other vertex] = INF
```

Here, `INF` represents “no path found yet.”

For an edge from `u` to `v` with weight `w`, the candidate path cost is:

$$
\text{candidate} = \text{dis}[u] + w
$$

If this is smaller than `dis[v]`, we have found a better path. This update is called **relaxation**:

```cpp
if (dis[u] + w < dis[v]) {
    dis[v] = dis[u] + w;
    if (w == 0) dq.push_front(v);
    else dq.push_back(v);
}
```

Only enqueue a vertex after a **strict improvement**. Equal-cost paths do not need another insertion when we are only finding distances. This also prevents a zero-weight cycle from repeatedly adding the same unchanged distances.

## 4. Discovered Is Not the Same as Settled

In ordinary BFS, the first discovery gives the shortest distance. In 0–1 BFS, a vertex's distance can improve after it has been inserted into the deque.

Consider this small undirected graph, scanning `1–2` before `1–3`:

```text
Edge       Weight
1 -- 2       1
1 -- 3       0
3 -- 2       0
```

From source 1:

1. Discover 2 with distance 1 and push it to the back.
2. Discover 3 with distance 0 and push it to the front. The deque is `[3, 2]`.
3. Remove 3. The zero-cost edge to 2 improves `dis[2]` from 1 to 0.
4. Push 2 to the front. The deque now contains `[2, 2]`.

The true shortest path to 2 is `1 -> 3 -> 2`, with cost 0, not the direct edge of cost 1.

If we marked 2 visited on its first insertion and refused later improvements, we would obtain the wrong answer.

### What Does `settled[u]` Mean?

In the implementation below, `settled[u]` means:

> Vertex `u` has been removed for processing with its final shortest distance, and its outgoing edges have been examined.

Mark it settled **when removing it from the front**, not when inserting it. If a later deque entry refers to an already settled vertex, skip that entry.

In the example, the first removal of 2 processes it at distance 0. The second occurrence is a duplicate and is ignored.

## 5. Why the Deque Rule Works

Think of each insertion as carrying the tentative distance at which it was inserted. At the start, the only candidate is the source at distance 0.

When processing the smallest useful candidate at distance `d`, every new candidate has distance either `d` or `d + 1`:

- A candidate at distance `d` goes to the front, before the next distance level.
- A candidate at distance `d + 1` goes to the back, after the current distance level.

Thus, useful candidates are processed in nondecreasing distance order. Entries left over from an earlier, worse distance do not require another expansion; they are skipped once their vertex is settled.

The code stores vertex IDs rather than distance snapshots. If a vertex occurs twice, both occurrences refer to its current `dis` value. The ordering argument concerns the candidate insertions, not a claim that reading `dis` for every duplicate ID in the deque always produces a sorted list.

### Why Can We Finalize a Vertex on Removal?

Suppose the first useful removal of `u` had a distance larger than the true shortest distance. Along a cheaper path to `u`, there would be an earlier vertex with a smaller candidate distance still needing processing. The deque's ordering would process that candidate first and propagate the improvement before settling `u`.

Therefore, when an unsettled vertex is removed from the front, its distance is final. Because weights are nonnegative, processing it cannot later be invalidated by a cheaper route through a larger-distance vertex.

Use source **1** and the edge order in the sample input below:

```text
1 -- 2 : 0
1 -- 3 : 1
2 -- 4 : 1
3 -- 4 : 1
4 -- 5 : 0
5 -- 6 : 0
4 -- 7 : 1
7 -- 6 : 1
```

Deque contents are shown **front to back**. Only successful improvements are listed.

| Vertex processed | Successful distance updates | Deque after processing |
| --- | --- | --- |
| — | `dis[1] = 0` | `[1]` |
| 1 | `dis[2] = 0` to front; `dis[3] = 1` to back | `[2, 3]` |
| 2 | `dis[4] = 1` to back | `[3, 4]` |
| 3 | None: cost 2 to vertex 4 is worse than 1 | `[4]` |
| 4 | `dis[5] = 1` to front; `dis[7] = 2` to back | `[5, 7]` |
| 5 | `dis[6] = 1` to front | `[6, 7]` |
| 6 | None: cost 2 to vertex 7 equals its current distance | `[7]` |
| 7 | None | `[]` |

Final distances:

| Vertex | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Minimum cost from 1 | 0 | 0 | 1 | 1 | 1 | 1 | 2 |

Vertices 4, 5, and 6 all have distance 1 because the edges `4–5` and `5–6` add no cost. Vertex 7 has distance 2, whether reached through 4 or through 6.

The processing sequence may depend on neighbour order, but the final shortest distances do not.

## 7. Complete C++17 Implementation

Each adjacency-list entry stores `(neighbour, edgeWeight)`.

### Input

- First line: `n m s`, the number of vertices, number of undirected edges, and source.
- Next `m` lines: `u v w`, with `w` equal to 0 or 1.
- Assume valid vertex labels from 1 to `n` and `n >= 1`.

### Output

Print the shortest distances to vertices 1 through `n`. Print `-1` for an unreachable vertex.

```cpp
#include <deque>
#include <iostream>
#include <limits>
#include <utility>
#include <vector>
using namespace std;

const int INF = numeric_limits<int>::max();

vector<int> zeroOneBfs(const vector<vector<pair<int, int>>>& g, int source) {
    int n = static_cast<int>(g.size()) - 1;
    vector<int> dis(n + 1, INF);
    vector<char> settled(n + 1, false);
    deque<int> dq;

    dis[source] = 0;
    dq.push_front(source);

    while (!dq.empty()) {
        int u = dq.front();
        dq.pop_front();

        // Duplicate entries must not cause repeated expansion.
        if (settled[u]) continue;
        settled[u] = true;

        for (auto [v, w] : g[u]) {
            if (settled[v]) continue;

            int candidate = dis[u] + w;
            if (candidate < dis[v]) {
                dis[v] = candidate;
                if (w == 0) dq.push_front(v);
                else dq.push_back(v);
            }
        }
    }

    return dis;
}

void solve() {
    int n, m, source;
    cin >> n >> m >> source;

    vector<vector<pair<int, int>>> g(n + 1);
    for (int i = 0; i < m; ++i) {
        int u, v, w;
        cin >> u >> v >> w;
        g[u].push_back({v, w});
        g[v].push_back({u, w}); // Remove this line for directed input.
    }

    vector<int> dis = zeroOneBfs(g, source);
    for (int u = 1; u <= n; ++u) {
        if (u > 1) cout << ' ';
        cout << (dis[u] == INF ? -1 : dis[u]);
    }
    cout << '\n';
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);
    solve();
    return 0;
}
```

Only vertices with finite distances enter the deque, so the code never adds a weight to `INF`. A shortest path can be chosen without repeated vertices because all weights are nonnegative; its cost is at most `n - 1`.

For a directed graph, add only `u -> v`. The shortest-path function itself does not change.

## 9. Complexity

Let `n` be the number of vertices and `m` the number of edges.

- Each vertex is settled and its adjacency list scanned at most once.
- Each scanned edge causes at most one successful relaxation and one deque insertion.
- Each deque insertion or removal takes constant time, including removals that only skip duplicates.

Therefore, the total time is **`O(n + m)`**. In an undirected graph, each edge appears twice in the adjacency lists; this constant factor does not change the bound.

The distance and settled arrays use `O(n)` space. Counting graph storage and pending deque entries gives an overall **`O(n + m)`** space bound. The deque may contain duplicate vertex IDs; it is not a visited-vertex set.

## 10. Common Mistakes and Useful Checks

- **Minimizing the number of edges:** the objective is minimum total weight; more edges can still cost less.
- **Marking visited on insertion:** an already discovered vertex can receive a better distance. Settle it on its first useful removal instead.
- **Using `dis[u] + 1` for every edge:** add the actual weight `w`.
- **Swapping the deque ends:** a zero-weight improvement goes to the front; a one-weight improvement goes to the back.
- **Enqueuing without strict improvement:** this adds unnecessary work and can loop indefinitely around zero-cost cycles in implementations without a settlement guard.
- **Treating every nonzero weight as 1:** the `else` branch is valid only because the input guarantees weights in `{0, 1}`. This is not a general weighted shortest-path algorithm.
- **Stopping when the destination is first discovered:** its distance may still improve. For a single-destination problem, stopping is safe when that vertex is removed as an unsettled vertex and finalized.
- **Returning 0 for unreachable vertices:** 0 is a valid reachable distance; use a separate sentinel such as `INF`, printed here as `-1`.

As sanity checks: with all weights 1, the distances match ordinary BFS; with all weights 0, every vertex reachable from the source has distance 0.

## Quick Recap

- 0–1 BFS finds minimum total costs when every edge weight is 0 or 1.
- Relax an edge only if it strictly improves the destination's distance.
- Push zero-weight improvements to the front and one-weight improvements to the back.
- Discovery is provisional; settle a vertex when processing its first useful removal.
- With duplicate entries skipped, the algorithm runs in `O(n + m)` time.
